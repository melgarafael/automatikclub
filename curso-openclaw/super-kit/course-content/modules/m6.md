# M6 — Seguranca e Blindagem

## M6A1 — Gerenciando Senhas com 1Password
**Conceito-chave:** Um cofre criptografado centraliza todas as credenciais dos seus agentes — API keys, tokens, senhas de ERPs — em um unico lugar auditavel e seguro.
**O que o aluno faz:** Criar conta no 1Password, configurar vaults separados por contexto (pessoal, sistemas, infra, financeiro), e salvar as credenciais do agente com campos padronizados.
**Conteudo principal:**
- Por que: agentes que executam processos acumulam dezenas de credenciais (OpenAI, Stripe, ERPs, bancos, gateways)
- Setup: criar conta, salvar Emergency Kit em local fisico, instalar extensao do navegador, ativar 2FA
- 4 vaults recomendados: Pessoal, Sistemas do Negocio, Infraestrutura, Sistemas Financeiros
- Campos padrao para API Key: nome (qual agente usa), key, URL do servico, notas (limite, data criacao)
- Boas praticas: uma key por agente, rotacao trimestral, limites de gasto, nunca compartilhar por chat, auditoria mensal
**Erros comuns:**
- Guardar API keys em WhatsApp, .txt na area de trabalho ou corpo de email
- Reutilizar a mesma key em multiplos agentes (se vazar, todos ficam vulneraveis)
- Nao salvar o Emergency Kit (perde acesso permanente ao cofre)
**Dica pratica:** Use tags como "producao", "desenvolvimento" e "teste" para filtrar rapidamente suas credenciais quando tiver multiplos agentes.

## M6A2 — Credenciais de Sistemas: Variaveis de Ambiente e Secrets
**Conceito-chave:** Credenciais nunca vao no codigo — vivem em variaveis de ambiente (.env) que ficam fora do repositorio, protegidas pelo .gitignore.
**O que o aluno faz:** Criar arquivo .env com todas as credenciais, configurar .gitignore, criar .env.example como documentacao, e configurar variaveis no servidor de producao via SSH.
**Conteudo principal:**
- Erro #1: hardcodar credenciais no codigo (bots varrem GitHub 24/7, casos de R$50k+ em cobranças indevidas)
- Antes/depois: stripe.api_key = "sk_live_..." (ERRADO) vs stripe.api_key = os.getenv("STRIPE_SECRET_KEY") (CORRETO)
- Arquivo .env com variaveis: OPENAI_API_KEY, STRIPE_SECRET_KEY, DATABASE_URL, ERP_API_TOKEN, OPENCLAW_SECRET
- .gitignore obrigatorio: .env, .env.local, .env.production, *.key, *.pem
- .env.example: mesmas variaveis sem valores reais, vai pro repositorio como documentacao
- Producao: configurar variaveis via SSH com export no .bashrc
**Erros comuns:**
- Commitar .env no Git antes de adicionar ao .gitignore (historico mantem a key exposta para sempre)
- Nao criar .env.example (proximo dev nao sabe quais variaveis precisa)
- Esquecer spending limits nos provedores (API key exposta = conta explodindo)
**Dica pratica:** Se voce ja commitou uma key, revogar imediatamente e gerar nova. Nao basta remover do codigo — o historico do Git mantem tudo.

## M6A3 — Prompt Injection: Protegendo Processos Criticos
**Conceito-chave:** Prompt Injection faz o agente ignorar instrucoes originais e executar comandos nao autorizados — especialmente perigoso quando o agente opera processos financeiros e operacionais reais.
**O que o aluno faz:** Entender os 4 tipos de ataque (direto, indireto, jailbreak, exfiltracao), implementar 5 tecnicas de defesa, e testar o agente com prompts maliciosos.
**Conteudo principal:**
- 3 exemplos visuais de ataque: manipulacao de cobranca ("marque como pago"), manipulacao de relatorio (instrucao oculta nos dados), manipulacao de estoque ("zere as quantidades")
- 4 tipos: direto (comando no chat), indireto (instrucao oculta em documentos), jailbreak (roleplay/cenarios), exfiltracao (vazar dados para canais externos)
- 5 defesas: double-check em processos criticos, log imutavel de acoes, aprovacao humana acima de threshold, separacao de contexto + menor privilegio, monitoramento de padroes anomalos
- OpenClaw ja implementa separacao de contexto e logs; thresholds e aprovacao humana sao responsabilidade do criador
**Erros comuns:**
- Nao definir thresholds financeiros (agente processa estorno de R$15k sem aprovacao)
- Dar acesso a todos os sistemas (mais sistemas = mais superficie de ataque)
- Nao testar com prompts maliciosos antes de ir pra producao
**Dica pratica:** Configure alertas para palavras como "ignore", "simule", "como teste" — sao sinais classicos de tentativa de injection.
**Aula anterior:** M6A2 | **Proxima:** M6A4

## M6A4 — Permissoes e Escopo: O Que o Agente Pode e Nao Pode Fazer
**Conceito-chave:** A pergunta nao e "o agente consegue fazer isso?" e sim "o agente deveria fazer isso sem aprovacao humana?" — limites claros previnem dano financeiro real.
**O que o aluno faz:** Classificar cada acao por nivel (leitura/escrita limitada/financeiro/exclusao/config), definir thresholds financeiros, configurar log de auditoria, e implementar kill switch.
**Conteudo principal:**
- Matriz de permissoes: leitura (livre), escrita limitada (livre+log), financeiro ate R$500 (automatico+double-check), financeiro acima R$500 (aprovacao humana), exclusao (aprovacao humana), alteracao config (apenas humano)
- 3 niveis de execucao: somente leitura, execucao limitada (ate R$500), execucao plena (aprovacao humana)
- 4 passos de configuracao: listar sistemas conectados, classificar acoes por nivel, definir thresholds, ativar log de auditoria
- Kill switch obrigatorio: botao de emergencia acessivel por celular 24/7 — sem kill switch nao vai pra producao
- Principio do menor privilegio: comece com minimo e va expandindo
**Erros comuns:**
- Permissao irrestrita em todos os sistemas (um erro/manipulacao = dano financeiro real)
- Sem kill switch (agente em loop de cobrancas sem como parar)
- Thresholds generosos demais no inicio (R$5000 sem aprovacao e muito para comecar)
**Dica pratica:** Comece com threshold de R$500 e va subindo conforme ganha confianca. E mais seguro adicionar permissoes do que restringir depois de um incidente.

## M6A5 — Backup e Recovery
**Conceito-chave:** Sem backup, uma edicao errada no system prompt, um hack ou problema no servidor pode destruir semanas de trabalho — backup e a garantia de que voce volta ao estado funcional rapidamente.
**O que o aluno faz:** Criar estrutura de pastas de backup, salvar system prompts com versionamento por data, configurar rotina de backup (antes de mudanca/semanal/mensal), e testar restauracao.
**Conteudo principal:**
- O que fazer backup: system prompts, configuracoes do OpenClaw, lista de credenciais em uso, workflows/SOPs, dados operacionais
- Rotina: antes de cada mudanca (prompt atual), semanal (configs + workflows), mensal (snapshot do servidor)
- Como criar snapshot na HostGator: cPanel → Backup Wizard → Backup Completo → download .tar.gz
- Estrutura de pastas: backups/prompts/ (com data), backups/configs/, backups/operacional/
- Como restaurar: cPanel → Backup Wizard → Restaurar → upload .tar.gz (cuidado: sobrescreve dados atuais)
**Erros comuns:**
- Editar system prompt sem salvar versao anterior (impossivel reverter)
- Fazer backup mas nunca testar restauracao (so descobre que nao funciona na hora da crise)
- Backup apenas no mesmo servidor (se servidor cair, backup vai junto)
**Dica pratica:** A forma mais simples e importante de backup: salvar prompts como .txt com data antes de qualquer edicao. Leva 10 segundos e ja salvou muita gente.
**Aula anterior:** M6A4 | **Proxima:** M7A1
