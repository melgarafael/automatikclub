# M3 — Identidade e Contexto: Configurando Para o Seu Negócio

> 7 aulas | ~90 min de leitura total | Do setup à memória operacional

---

## M3A1 — Instalando o Starter Kit
**Conceito-chave:** O Starter Kit transforma um OpenClaw genérico em agente executor com estrutura de pastas pronta para configurar.
**O que o aluno faz:** Roda `npm run install-starter-kit` na VPS e verifica que toda a estrutura de pastas foi criada.
**Conteúdo principal:**
- Kit inclui 4 componentes: Soul File (papel operacional), Agents.md (processos/regras), User Config (quem delega tarefas), Templates (modelos de processos)
- Estrutura: `soul/`, `agents/`, `config/`, `skills/`, `memory/`, `integrations/`
- Comando de instalação: `cd ~/openclaw && npm run install-starter-kit`
- Não editar nada ainda — cada arquivo será configurado nas aulas seguintes
**Erros comuns:**
- Tentar configurar os arquivos antes de entender cada um (causa inconsistências)
- Rodar o comando fora da pasta do OpenClaw
**Dica prática:** Confirme que todas as 6 pastas foram criadas antes de seguir. Se faltou alguma, rode o comando novamente.
**Aula anterior:** M2A6 | **Próxima:** M3A2

---

## M3A2 — Definindo a Soul do Seu Agente
**Conceito-chave:** A Soul define o papel operacional do agente — qual cargo ele ocupa e quais processos executa no negócio.
**O que o aluno faz:** Cria o arquivo `soul/soul.md` com identidade, regras operacionais, estilo de execução e limites de escalação.
**Conteúdo principal:**
- Template: Identidade (nome, papel, domínio), Regras Operacionais, Estilo de Execução (relatórios, confirmação, notificações), Limites e Escalação
- Antes/Depois: genérico ("Como posso ajudar?") vs operacional ("Operador financeiro. Tarefas: relatórios de fluxo de caixa, cobranças, monitorar inadimplência")
- 4 tipos de agente: Financeiro, Operacional, Comercial, Administrativo — cada um com exemplo concreto de execução
- Soul vaga = execução inconsistente. Definir processos específicos, não descrições genéricas
- Testar com 5 tarefas diferentes antes de prosseguir
**Erros comuns:**
- Escrever descrição genérica ("assistente útil") ao invés de papel operacional específico
- Não definir limites de escalação — agente toma decisões que deveria escalar
- Pular o teste de 5 tarefas
**Dica prática:** Defina o papel como cargo operacional ("gerente de operações" executa melhor que "assistente virtual") — a IA trata o cargo como âncora de comportamento.
**Aula anterior:** M3A1 | **Próxima:** M3A3

## M3A3 — O Arquivo Agents.md
**Conceito-chave:** Agents.md é o manual de processos — define quais tarefas o agente executa, como opera, e quando escalar. Se a Soul diz *quem ele é*, o Agents.md diz *como ele opera*.
**O que o aluno faz:** Cria `agents/agents.md` com 4 seções obrigatórias preenchidas para o negócio real do aluno.
**Conteúdo principal:**
- 4 seções obrigatórias: Contexto Operacional (empresa, sistemas, horários, permissões), Processos (lista explícita de tarefas com triggers), Regras Operacionais (DEVE e NÃO DEVE), Limites e Escalação (quando parar e pedir humano)
- Exemplo completo: Operador Financeiro da TechCorp com processos de fluxo de caixa, cobranças, inadimplência, comissões
- Regras: SEMPRE registrar log, NUNCA processar >R$50k sem aprovação, confirmar TODOS pagamentos, gerar backup antes de alteração em massa
- Nunca colocar credenciais no Agents.md — usar .env
**Erros comuns:**
- Processos vagos ("cuidar do financeiro" vs "gerar relatório diário de fluxo de caixa")
- Não definir regras de escalação — agente executa ações fora do escopo
- Colocar tokens ou senhas no arquivo (deve ir no .env)
**Dica prática:** Quanto mais específicos os processos, melhor a execução. "Processar cobranças vencidas há mais de 5 dias" > "cuidar das cobranças".
**Aula anterior:** M3A2 | **Próxima:** M3A4

## M3A4 — Usuários e Permissões
**Conceito-chave:** O arquivo users.json controla quem pode delegar tarefas ao agente e com qual nível de autonomia, usando roles com rate limits.
**O que o aluno faz:** Configura `config/users.json` com roles (owner, manager, team, system) e aplica com `npm run apply-config`.
**Conteúdo principal:**
- 4 roles padrão: owner (tudo, sem limite), manager (delegar/executar/monitorar, 50/h), team (delegar básico, 20/h), system (execução agendada/triggers, 100/h)
- Permissões: delegate, execute, approve, monitor, configure, delegate_basic, view_own, execute_scheduled, trigger
- Rate limits protegem API key e controlam custo — configurar SEMPRE, mesmo em projetos pequenos
- Aplicar config: `npm run apply-config`
**Erros comuns:**
- Não configurar rate limits (um trigger pode gerar centenas de execuções)
- Dar permissão ampla demais no início — difícil revogar depois
**Dica prática:** Comece restritivo e vá liberando. É mais fácil conceder permissão do que revogar.
**Aula anterior:** M3A3 | **Próxima:** M3A5

## M3A5 — Conectando ao Telegram
**Conceito-chave:** O Telegram com tópicos é o canal operacional do agente — recebe comandos, entrega relatórios, notifica alertas e registra logs.
**O que o aluno faz:** Cria bot no BotFather, configura grupo operacional com tópicos (Tarefas, Relatórios, Alertas, Logs), testa comando real.
**Conteúdo principal:**
- Criar bot: @BotFather → /newbot → copiar token → salvar no .env
- Grupo operacional com tópicos: Tarefas (recebe comandos), Relatórios (outputs), Alertas (anomalias), Logs (registro de execuções)
- Teste: enviar `/relatorio vendas hoje` no tópico Tarefas → agente processa → resultado no tópico Relatórios
- Bot como admin do grupo com permissões de envio e gerenciamento de tópicos
**Erros comuns:**
- Token do bot vazar publicamente (revogar imediatamente no @BotFather)
- Não ativar tópicos no grupo (perde a organização de fluxos)
- Não adicionar bot como admin (não consegue enviar mensagens)
**Dica prática:** Tópicos no Telegram separam fluxos operacionais: Tarefas recebe comandos, Relatórios recebe outputs, Alertas notifica anomalias.
**Aula anterior:** M3A4 | **Próxima:** M3A6

## M3A6 — Organizando seu Workspace
**Conceito-chave:** Estrutura de pastas organizada e convenções de nomes garantem que o agente encontre e armazene dados corretamente durante execuções.
**O que o aluno faz:** Cria estrutura completa de pastas e entende o fluxo de execução: Comando → Soul → Processos → Skills → Sistemas.
**Conteúdo principal:**
- Estrutura: `soul/`, `agents/`, `config/`, `skills/` (operacionais), `memory/` (short-term + long-term), `integrations/` (telegram, database, api), `logs/`
- Convenções: pastas/arquivos em kebab-case, variáveis em SCREAMING_SNAKE
- Fluxo de execução: Comando → Soul (papel) → Processos (regras) → Skills (ações) → Sistemas (dados)
- Criar estrutura agora mesmo que pastas fiquem vazias — facilita adicionar skills e integrações depois
**Erros comuns:**
- Misturar convenções de nomes (FluxoCaixa vs fluxo-caixa)
- Não criar pastas de logs e memory desde o início
**Dica prática:** Crie toda a estrutura agora, mesmo vazia. Você vai agradecer quando precisar adicionar nova skill ou integração.
**Aula anterior:** M3A5 | **Próxima:** M3A7

## M3A7 — Memória do Agente
**Conceito-chave:** Memória transforma o agente de executor genérico em operador inteligente que aprende padrões do negócio ao longo do tempo.
**O que o aluno faz:** Configura os 3 tipos de memória no `settings.json` com TTL, limites e campos sensíveis protegidos.
**Conteúdo principal:**
- 3 tipos: Curto prazo (sessão/tarefa, ex: "processando lote de 47 cobranças"), Longo prazo (permanente, ex: "Cliente ABC atrasa 8 dias em média"), Compartilhada (permanente, ex: "margem mínima 15%, SLA 2h")
- Config no settings.json: short_term (max 50, TTL 24h), long_term (max 1000, auto_summarize), shared (scope: organization)
- Campo `sensitive_fields`: CPF, cartão, senha, conta bancária — agente processa mas não retém
- LGPD: configurar exclusão de dados ANTES de produção. Multa até 2% do faturamento
- Boas práticas: salvar apenas o operacionalmente relevante, TTL para contexto de tarefa, nunca memorizar dados financeiros sensíveis
**Erros comuns:**
- Armazenar CPF/dados bancários na memória (violação de LGPD)
- Não configurar TTL para memória de curto prazo (acumula lixo)
- Não implementar comando de exclusão de dados antes de produção
**Dica prática:** Memória é a diferença entre "processar cobrança genérica" e "cobrar cliente ABC que atrasa 8 dias, usando a abordagem que funcionou nas últimas 3 vezes, no horário que ele responde (14h-16h)".
**Aula anterior:** M3A6 | **Próxima:** M4A1
